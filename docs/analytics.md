# Phase 31 learning analytics

Phase 31 defines minimized learning measurement. Both applications leave PostHog capture **off by default**. No project key, external destination or real learner collection is configured in this repository. [F06](decisions.md) requires approved consent, retention, deletion, backup and operator-access policies before any real learner data is sent, including during beta. [F05](decisions.md) still owns numerical targets, recruitment, sample size and review windows; the definitions below are not efficacy claims.

## Event dictionary and trust

The capture boundary accepts only contract version `1`, `event_id`, `source_trust`, `cohort`, and bounded `quest_id`, `chapter_id`, `content_version`, `assessment_version`, `outcome_category` or `error_category` where relevant. Backend submissions also carry `client_reported: true`, reflecting [ADR 0005](adr/0005-assessment-trust-and-completion.md). Browser events carry no grading authority. Neither application sends source, output, reports, written responses, hint text, URL/query strings, email, tokens or free text. Browser Run/Check callbacks contain an outcome only, never the editor snapshot.

| Event                   | Source                                            | Meaning and event identity                                                                             |
| ----------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `signup_completed`      | Backend fact, account                             | First CodeQuest owner row from an authenticated account or learning write; owner ID                    |
| `first_quest_started`   | Backend fact, account; browser observation, guest | First account quest-start fact or first guest start in a tab; account quest ID or ephemeral browser ID |
| `first_code_run`        | Browser observation, guest/account                | First non-cancelled Run observed in the current tab; random event ID                                   |
| `code_run`              | Browser observation, guest/account                | Every non-cancelled Run, including later successful work; status category only, random ID              |
| `validation_checked`    | Browser observation, guest/account                | Every completed local Check, passing or failing; pass/fail category only, random ID                    |
| `first_quest_completed` | Backend fact, account                             | First accepted quest completion; attempt ID                                                            |
| `quest_attempted`       | Backend fact, account                             | New persisted submission, including failed attempts and later practice; attempt ID                     |
| `quest_failed`          | Backend fact, account                             | New persisted failed submission; attempt ID                                                            |
| `quest_completed`       | Backend fact, account                             | New first accepted completion for a stable quest ID; attempt ID                                        |
| `hint_used`             | Backend fact, account; browser observation, guest | New owner/quest/version/hint-key fact or observed guest hint opening; composite fact or random ID      |
| `execution_error`       | Browser observation, guest/account                | Non-cancelled Run error category, not error text; random ID                                            |
| `validation_failed`     | Browser observation, guest/account                | Failed local Check, without report or source; random ID                                                |
| `capstone_started`      | Backend fact, account                             | New capstone start fact; stable quest ID                                                               |
| `capstone_completed`    | Backend fact, account                             | First accepted capstone completion; attempt ID                                                         |
| `streak_continued`      | Backend fact, account                             | First credited consecutive local streak day from an accepted completion; attempt ID                    |

Backend event timestamps come from persisted facts and are emitted only after their transaction resolves. `signup_completed` is the first verified CodeQuest owner-row write, a backend-observable proxy for account activation; it is not the Supabase registration instant. An authenticated learner who only reads public content has no CodeQuest signup event yet, and funnel reports must disclose that gap. Account and guest cohorts never merge automatically, including on guest import. Guest identifiers are ephemeral to the enabled browser tab, so browser clearing and multiple devices cause known gaps. Exact submission replay emits no new fact event; passing practice on an already completed quest emits an attempt but no second accepted milestone. Provider failure cannot change completion, XP, streaks or unlocks. PostHog delivery is best effort, so reports deduplicate `event_id` and stable quest identities; the provider is not treated as an exactly-once ledger.

## Enabling policy and transport

Backend delivery requires `ANALYTICS_CAPTURE_APPROVED=true`, `POSTHOG_PROJECT_KEY` and an HTTPS `POSTHOG_HOST`. Browser delivery separately requires `NEXT_PUBLIC_ANALYTICS_CAPTURE_APPROVED=true`, `NEXT_PUBLIC_POSTHOG_PROJECT_KEY` and `NEXT_PUBLIC_POSTHOG_HOST` at build time. The approval switches must remain unset until F06 has an approved operational policy. An invalid or incomplete combination makes no request. The browser uses `credentials: omit`, `referrerPolicy: no-referrer`, and no credential-bearing header. The direct custom-event adapter has no automatic page/click/form capture, replay, survey, identify, feature-flag polling or exception capture. Worker and preview origins have `connect-src 'none'` and cannot import the application adapter. Tests use fake capture transports or intercepted destinations, never a live project key.

## Query definitions

Filter every report to `properties.contract_version = 1`. Report `source_trust` and `cohort` as separate dimensions; never combine guest observations with accepted account numerators. Deduplicate by `event_id` before aggregation. For accepted quests, additionally deduplicate by `(distinct_id, quest_id)` and only count backend `quest_completed` with `client_reported = true`. The published curriculum mapping and current content/assessment compatibility policy determine each chapter's required quest IDs. Old incompatible completions do not silently satisfy a current-chapter funnel step.

| View                    | Numerator                                                                                                  | Denominator and window                                                                                    |
| ----------------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| First run activation    | Distinct cohort IDs with `first_code_run` after a first quest start                                        | Distinct first quest starters, same guest/account cohort and first session                                |
| First accepted quest    | Accounts with `first_quest_completed`                                                                      | Account first quest starters whose 24-hour window elapsed                                                 |
| Five quests             | Accounts with at least five distinct accepted `quest_id` values from `quest_completed`                     | Accounts activated by a first accepted completion, within 7 elapsed days                                  |
| First completed chapter | Accounts whose set of compatible accepted quest IDs covers every published requirement for any one chapter | Accounts with a `first_quest_started` in that chapter, within 7 elapsed days of that start                |
| Capstone start          | Accounts with a backend `capstone_started`                                                                 | Accounts eligible for CAP01 from compatible accepted prerequisites, within 14 elapsed days of eligibility |
| Capstone completion     | Accounts with `capstone_completed`                                                                         | Capstone starters whose full 14-day observation window elapsed                                            |

Daily and weekly meaningful activity are **derived views**, not events sent on app open. They count distinct cohort IDs with `code_run`, `validation_checked`, backend `quest_attempted` or accepted `quest_completed` in each UTC day or ISO week. They must retain the source label and omit app opens. D1 return is a new qualified action at elapsed 24–48 hours after cohort activation; D7 is the same at elapsed 168–192 hours. A denominator includes only activated learners whose entire window has elapsed at the reporting cutoff. For guest observed cohorts, use browser activity only; for accepted-account cohorts, report observed interaction and backend submission/completion evidence separately. The timezone-local `streak_continued` day is never substituted for an elapsed D1/D7 window. Show numerator, denominator, window cutoff, sample size, missing-browser-data caveat and content version for every chart.

The funnel order is **signup → first Run → first accepted quest → five distinct accepted quests → first completed chapter → capstone start → accepted capstone completion**. The first Run is a client observation, while the later acceptance steps come from backend facts. Stage counts use unique account IDs that have all earlier stages in order; a replayed attempt does not create a second stage. Signup before a guest Run is a separate account funnel because no automatic guest identity stitching is approved.

The deterministic [measurement fixture](../backend/src/modules/analytics/measurement-fixture.spec.ts) uses three synthetic accounts. A duplicate Q01 event for A leaves A at two distinct accepted quests; C has five. At a 50-hour cutoff, A and C have a qualified D1 action and B has only an app open, so D1 is **2/3**. At a 200-hour cutoff, only C has a qualified D7 action, so D7 is **1/3**. A 180-hour cutoff excludes all three from the D7 denominator because the full 192-hour window has not elapsed.
