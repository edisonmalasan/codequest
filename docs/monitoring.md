# Phase 32 monitoring

CodeQuest's Sentry delivery is **disabled by default**. The backend keeps its existing structured request completion and unexpected error logs. The browser and API adapters send only fixed operational categories and allowlisted metadata. Learner source, validation output, request/response bodies, dynamic URL values, tokens and user identities are excluded. Worker execution and preview origins do not import monitoring.

## Enablement gate

Do not enable collection for real learners until decision F06 has approved consent, retention, deletion and operator access. Before a deployment, configure Sentry project IP scrubbing and inbound data filters, restrict project access, choose alert recipients and retention, and verify the deployment's privacy notice. These policies and Sentry projects are external to this repository and are not yet operational.

For an approved deployment, set backend `MONITORING_CAPTURE_APPROVED=true`, `SENTRY_DSN` and `CODEQUEST_RELEASE`. The browser build uses `NEXT_PUBLIC_MONITORING_CAPTURE_APPROVED=true`, `NEXT_PUBLIC_SENTRY_DSN` and `NEXT_PUBLIC_CODEQUEST_RELEASE`. Each DSN must be a valid HTTPS Sentry DSN; the release is a 1–64 character alphanumeric/dot/underscore/dash label. A missing or invalid value disables that adapter. `MONITORING_SLOW_MS` may set the backend slow request threshold from 100 to 60000 ms; the default is 1000 ms. Browser values are baked into the build and require a new build to change. The repository ships with no approval flag or DSN.

The SDKs disable default integrations, tracing, automatic error and breadcrumb collection. Capture uses fixed messages and strips the SDK event to an allowlist before delivery. The backend reports all 4xx/5xx status classes, all requests at or above the slow threshold, and a deterministic 1% sample of other successes. An unexpected exception is separately reported once, with a safe class. Its completion status report is a distinct latency/status signal. The browser reports route render failures and application-origin uncaught errors or unhandled promise failures. It does not report learner execution failures, and it skips capture while offline.

## Triage and verification

For a failed API request, use the response's `x-request-id` to find the matching `request.completed` and `request.failed` structured logs, then compare the Sentry `request_id`, route template, method, status class and bounded duration. Build failed-request and latency views from `api_request` categories (`client_failure`, `server_failure`, `slow_request`, `sampled_request`); route errors use `frontend_failure`, and unexpected server exceptions use `api_exception`. Use release and environment labels to compare deployments. Configure alerts for server failures and elevated slow-request counts and verify their destination in the Sentry project before relying on them.

Synthetic verification uses only fake local sinks in repository tests. The focused monitoring suites exercise approved test releases, invalid configuration, SDK payload filtering with canary source/token/URL text, 400/500/unmatched route signals, recovery UI, and sink failure. No external Sentry request is made. A production rollout should repeat a synthetic failure against its approved project and inspect the final stored event for private fields before enabling general traffic. Neither dashboards nor alerts are claimed to be live here.
