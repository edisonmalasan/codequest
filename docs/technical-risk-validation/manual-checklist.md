# Phase 1 device validation procedures

**Current execution instruction (2026-09-14):** Codex performs all available validation through browser/CDP/automation tools and must not request manual user validation. These procedures preserve the original physical/device acceptance methods for future accessible configurations; they are not a current request for manual participation. See the [proposed scope adjustment](proposed-scope-adjustment.md).

Only the Windows development machine and installed Chrome are confirmed. Execute the Windows checklist separately in installed Chrome and Firefox if available; record actual versions, not Playwright engine versions. macOS, Android, iPhone, NVDA and VoiceOver remain **untested** until explicit access is confirmed. The [charter](charter.md) B01-B09 criteria remain unchanged.

Use synthetic data and a separate task browser profile. The redesigned **Open bounded preview** runs learner functions in a restricted Worker and displays fixed, script-disabled supplied-shell output. Do not manually run the historical executable-HTML `__risk.preview` comparison: it previously required emergency termination. Automated preview success does not replace physical or accessibility evidence.

## Windows physical editing and learning loop (tasks 3.2, 8.2)

1. Read Q01. Run the starter, then Check: execution succeeds but the answer fails. Read the hint, physically type `console.log("Ready for CodeQuest");`, Check and verify provisional completion; wait for actual Saved state.
2. Physically select words/multiple lines, paste synthetic text, indent and undo/redo. Resize the window and reach instructions/output/actions. Type immediately before switching Q01/RECORDS or owners, return and reload: compare exact source. Record lost edits or inaccessible controls.
3. Cancel Reset source, then accept it. Verify cancellation preserves source and reset changes the draft only, with truthful unsaved/saved states.
4. Select RECORDS and use the supplied `summarize(records)` fixture. Run and Open bounded preview: verify total 5 visually and Text equivalent: 5. Change the result, rerun and compare current source/output.
5. Save a pending synthetic snapshot, switch guest/account A/account B/expired, explicitly import guest work and retry a lost response. Confirm originating-owner isolation, immutable pending source, no duplicate simulated reward and accurate provisional/simulated-acceptance labels. This is not production authorization evidence.
6. For B01 collect **10 warmup and 100 measured physical edit interactions**, each monotonic input-to-rendered-source-update sample and nearest-rank p95. Required p95 is <=100 ms on the declared lower-powered device. Retain browser input/rendering traces and measurement boundaries for analysis. Subjective speed or a coarse stopwatch cannot pass this gate; if measurement/analysis cannot be completed, mark latency untested and retain the trace for analysis.

## Windows keyboard, zoom/reflow and reduced motion (task 3.3)

1. Put the mouse aside. Tab/Shift+Tab through instructions, editor, Run/Check/Stop, hint/reset/copy, feedback, reconciliation and preview. Record order, visible focus and unreachable controls.
2. Press Escape inside the editor: focus must move to Run. Activate each essential action with the keyboard; record traps and source loss.
3. Trigger syntax error, runtime error and wrong answer. Inspect distinct feedback and source/output; reach the textual preview without entering the iframe.
4. Repeat essential reading/editing/actions at **200% and 400% zoom** and a **320-CSS-pixel viewport**. Record clipping, overlap, lost focus/source and scrolling that prevents essential use.
5. Enable reduced-motion preference and repeat navigation/actions. Record any essential information conveyed only by motion. These checks do not establish NVDA/VoiceOver comprehension or a complete accessibility audit.

## Windows runtime, preview/security and resources (tasks 4.3, 5.2, 6.2, 6.3)

1. Close DevTools for representative timing. Run success, syntax-error and runtime-error sources; verify distinct states and exact source retention.
2. Enter `while(true){}`. Test **Run and Open bounded preview separately, 10 trials each**. During execution toggle Show hint or change focus: the trusted host must stay usable. Record dispatch, timeout/recovery feedback and source before/after. B02 is a **2-second deadline plus at most 1 second recovery**; any emergency browser/process killing, crash or source loss fails. For raw monotonic timing on RECORDS, use the trusted harness delegate in task DevTools: `window.__manualSourceBefore = window.__risk.source(); window.__manualTrial = window.__risk.previewSource(window.__manualSourceBefore, "RECORDS")`; close DevTools and exercise the host while it runs, then reopen and retain `JSON.stringify({ result: await window.__manualTrial, before: window.__manualSourceBefore, after: window.__risk.source() })`. This passes a source string to the restricted Worker, never evaluates it in the host. For Worker trials substitute `window.__risk.run(window.__manualSourceBefore, "opaque", "RECORDS")`. Label these physical-browser instrumented trials separately from normal-button usability observations.
3. After each timeout restore valid source and start a fresh run/preview. Record **10 fresh-run trials**, <=1 second to readiness (B03). Use visual readiness/recording or load/render instrumentation for preview readiness: a successful preview promise deliberately resolves after its two-second presentation reset, so promise duration is not B03 readiness. Explicitly Stop an active Worker run/preview and verify later execution works.
4. Repeat the committed online probe source strings from `prototypes/technical-risk-validation/tests/security.spec.ts` through the harness: copy only each learner `source` string into the editor, select opaque or dedicated as specified, then Run; for RECORDS/preview use Open bounded preview. Do not execute those source strings in the trusted console. For each probe reset the local sink with `Invoke-WebRequest http://127.0.0.1:4312/reset -Method Post`, retain requests using `Invoke-WebRequest http://127.0.0.1:4312/records`, and record source/result/expected denial. Verify a trusted positive-control request reaches the sink before denial trials; a silent or unreachable sink is inconclusive. Record effective sandbox/CSP in browser DevTools for policy inspection, closing DevTools for timing trials. Cache/channel/cookie canaries and wrong-source injection require the trusted fixture setup in the same test file; leave any probe whose setup is not completed untested and retain evidence for assisted analysis. Hostile HTML/CSS returned by learner source must be inert text, not executable DOM. Never paste arbitrary learner source into the host DevTools console for execution.
5. Execute **100 Worker and 100 executed preview/reset cycles per desktop browser**, first 10 warmup within each total. Record raw timings, exact source/task/version and cleanup per cycle plus retained-memory/resource observations after warmup/cleanup. In-browser instrumentation can assist repeated cycles, labeled physical-browser instrumentation rather than physical typing. Successful cleanup does not establish a hard browser memory quota.

## Windows physical cold offline, installation and storage (tasks 7.2, 7.3)

1. Prepare Q01/RECORDS online, save uniquely identifiable source, record exact source hash/content/assessment versions and confirm execution/preview work. Use the canonical app URL.
2. Record actual PWA installation support. Install only in the task profile if exposed and test installed mode separately. If unavailable, record installation as unsupported with evidence; ordinary browser learning remains required.
3. Close all task browser/app windows and verify those task processes ended; preserve ordinary sessions. Disconnect the actual external network and record that condition. Loopback remains reachable when Wi-Fi/Ethernet is disconnected, so also make the synthetic app origin unavailable: `Invoke-WebRequest "http://127.0.0.1:4310/__app-outage?enabled=true" -Method Post`. Confirm a direct uncached request receives 503 before relaunching the task profile/app and prepared lesson. Keep the fixture process running so its public origin can be restored, but do not count a load served by reachable source assets as offline success. A new tab or DevTools offline toggle is not a cold process launch. Restore with the same command using `enabled=false` after each trial; retain network/outage evidence separately.
4. Verify exact source/versions, read/edit/Check Q01 and run the preview offline. Completion remains provisional. Collect **10 physical cold-launch trials** on the declared lower-powered device: lesson/editor/local execution usable within **5 seconds**, retaining every sample.
5. Reconnect and verify owner/version state. Background/minimize, change network and resume; repeat browser restart and OS restart where practical, recording source/state before and after. Windows behavior does not supply mobile lifecycle coverage.
6. In task DevTools only set `window.__risk.saveFailure('full')`, edit and verify failure/copy recovery; reload and compare last confirmed source. Remove injection with `window.__risk.saveFailure(null)`. Keep injected failure separate from native storage evidence.
7. Test actual unavailable storage through a recorded task-profile setting if supported; clear only task-origin data to check truthful missing-resource/local-loss disclosure. Native full-storage testing requires a bounded isolated setup: **do not fill the system disk** or mark the unenforced CDP override passed. If no safe setup exists, retain native quota as untested/inconclusive.

## Windows exact update/persistence mix (tasks 7.4, 8.3)

1. Execute **8 save/reload cycles** with distinct confirmed source and immutable pending snapshots; compare exact source/owner/task/content/assessment identity each time.
2. Execute **6 waiting/activation update cycles** during editing with pending work. In a separate terminal increment public revision: `Invoke-WebRequest http://127.0.0.1:4310/__revision -Method Post`. In task DevTools request `(await navigator.serviceWorker.getRegistration()).update()`, then close DevTools for representative timing.
3. Observe available update. Injected save failure must pause activation; remove failure, use **Save draft and apply available update**, wait for actual activation and compare source/pending identity after reload.
4. Execute **6 multiclient update cycles** with two task tabs and distinct sources/pending conditions, checking originating-owner separation and each tab's confirmed identity. Total is exactly **20 cycles per required browser/mode**, not 20 reloads.
5. After update prepare canonical URL, cold relaunch offline and run Worker preview. Reconnect and repeat online containment/output probes. Retain sink/canary/source evidence. Use existing controlled version fixtures to verify incompatible identity rejection without source deletion/relabeling; do not invent a production curriculum change.
